Rockchip RK3588 Boards
======================

QEMU models four machines built around the Rockchip RK3588 SoC.  The
``rock-5b`` and ``rock-5b-plus`` models are the two ROCK 5B variants and
are documented together as the ROCK 5B family; the ``rk3588-evb`` and
``rk3588s-roc-pc`` models are the legacy RK3588 EVB and ROC-RK3588S-PC
boards.  All of them support Linux and firmware images built for Rockchip
RK3588 boards.  The ``rock-5b`` machine supports the current RK3588 SoC
device split; ``rock-5b-plus`` and the two EVB/ROC models use the legacy
machine implementation.

Implementation status
---------------------

Each RK3588 board has a self-contained machine implementation in its
own board file.  ``rock-5b`` uses the split RK3588 SoC device
(``hw/arm/rk3588.c``); ``rk3588-evb``, ``rk3588s-roc-pc`` and
``rock-5b-plus`` currently carry their existing device and
firmware-boot implementation directly in their board files.  There is
no shared ``rk3588-machine.c`` base; duplicated board code is
intentional while the board device sets are unified.

ROCK 5B
-------

The ``rock-5b`` machine models the Radxa ROCK 5B single-board computer,
which is built around the Rockchip RK3588 SoC.

Supported devices
~~~~~~~~~~~~~~~~~

The ``rock-5b`` machine supports the following devices:

* 4 Cortex-A55 and 4 Cortex-A76 CPUs
* GICv3 with two ITS blocks, including LPIs and MSI
* the architectural timers
* UART1 through UART9
* Rockchip SFC with a 16 MiB SPI NOR flash (XTX XT25F128)
* SPI0, SPI1 and SPI3, the three controllers routed to the 40-pin header
* GPIO0 through GPIO4 using the Rockchip GPIO v2 bank model
* Clock and reset unit (CRU); clock, soft-reset and vendor reset-status
  registers are modeled as storage registers with the Rockchip high-word
  write mask, including the reset read-back used by real firmware
* OTP controller
* Type-C USB port: DWC3 device-mode controller with a CDC ACM console bridge
* PCIe2x1l2 host bridge with an RTL8125 2.5GbE endpoint (RX/TX, MSI and
  PHY link state; attach a QEMU network backend with ``-nic``)
* SD/MMC controller (dw_mmc) with an SD card on ``if=sd,index=2``

The machine always uses all eight CPUs and supports 128 MiB to 16 GiB
of RAM, with 2 GiB as the default.

Peripheral mapping
~~~~~~~~~~~~~~~~~~

The machine models part of the RK3588 peripheral set.  The remaining windows
are mapped as unimplemented devices, so a guest access reads as zero and is
logged by ``-d unimp``.  The tables below give the SoC window, the GIC
interrupt, the ROCK 5B board connection and the modeling status of the
peripherals that a bring-up has to locate.

Window and interrupt numbers are those of ``rk3588_memmap[]``,
``rk3588_unimpl_devices[]`` and the ``RK3588_SPI0_SPI`` macro in
``hw/arm/rk3588.c``, and they match the RK3588 device tree.  Header pin
numbers, mux functions and header voltages are from Radxa's ROCK 5B hardware
interface documentation; the on-board wiring is from
``rk3588-rock-5b-5bp-5t.dtsi``.  Header mux names are the pinout names; the
device-tree pin groups are their lowercase form, with an ``_xfer`` suffix for
a data pair (``UART2_TX_M0``/``UART2_RX_M0`` are ``uart2m0_xfer``).

A GPIO is addressed as ``GPIO<bank>_<port><index>``: ``bank * 32 + port * 8 +
index``, with ports ``A`` to ``D``.  The number in the pin table follows that
formula, so ``GPIO4_B3`` is 139.  Bare numbers in the connection columns below
are 40-pin header positions.

From an ``aarch64-softmmu`` build directory, the bank-level test is run with::

  ninja tests/qtest/rk3588-gpio-test
  QTEST_QEMU_BINARY=./qemu-system-aarch64 ./tests/qtest/rk3588-gpio-test

Pin muxing itself lives in the IOC blocks, which the machine does not model,
so a guest cannot yet switch a pin between GPIO and a peripheral function.

I2C0 and I2C1 put the same bus on two different pin groups: the regulators
use ``_M2`` on the board while the header carries ``_M1`` and ``_M0``, so a
device plugged into the header shares the bus, and therefore the address
space, with a supply regulator.  That is a bus-level conflict, not a mux one:
the two pin groups cannot be active at the same time either, because a
controller drives one group at a time.

The SPI NOR flash is not on this list: it sits behind the SFC controller,
which is modeled, and is attached with ``-drive if=mtd,index=0`` as described
above.

The modeled controllers carry the qdev ids ``spi0``, ``spi1`` and ``spi3``, so
a peripheral can be attached to their bus by name.  A serial flash answers the
JEDEC read-ID command on SPI0 as follows::

  qemu-system-aarch64 -M rock-5b -m 256M -bios u-boot-dtb.bin \
      -serial null -display none -device n25q256a,bus=/spi0/spi/ \
      -monitor stdio

Program ``CTRLR0`` with an 8-bit frame format, set ``SER`` for chip select 0,
``SSIENR`` to enable the block and ``BAUDR`` for the bus clock, then push
``0x9f`` and three dummy bytes into ``TXDR``.  The receive FIFO returns
``00 20 ba 19``: the byte clocked out during the command, then the three ID
bytes of the ``n25q256a`` model.

The controllers drive the chip select of the peripheral attached to them, so
``SER`` alone selects the device; there is no separate GPIO to toggle.

Chip select polarity comes from bit 23 (chip select 0) and bit 24 (chip select
1) of ``CTRLR0``.  Setting bit 23 while the flash expects an active-low select
leaves it deselected, and the receive FIFO returns zeros.

The RK3588 has four PWM controllers, each with four channels, so a pinout name
such as ``PWM13_M0`` selects controller 3, channel 1 at ``0xfebf0010``.
``rk3588-pwm`` implements the TRM register layout, reset values,
``PWM_VERSION_ID``, independent channels, continuous left-aligned output, duty
and inactive polarity, live counters, enable/stop, period/duty/control shadow
updates at period boundaries, and ``conlock`` staging.  Migration preserves
the register file, active waveform configuration, counter epoch, pending
timer and output-line levels.  The input clock can be selected with
``clk_src_sel`` between the configurable PLL root clock ``clock-hz`` and the
fixed oscillator root clock ``osc-clock-hz``; both default to 24 MHz on
ROCK 5B.  Zero and full duty produce valid flat 0% and 100% outputs.  Zero
period and duty greater than period are diagnosed as invalid guest
configurations and do not generate a waveform.  The model exposes four named
``pwm-out`` lines per controller for board wiring and qtests.

``PWM_VERSION_ID`` follows TRM V1.0 section 18.4.1 (page 1411,
``0x02120B34``); section 18.4.2 (page 1425) instead gives
``0x021311B6`` and marks the fields RW.

The IRQ column lists GIC SPI numbers.  The corresponding GIC INTIDs are SPI
plus 32, giving INTIDs 376 to 383.  The TRM assigns a main IRQ and a channel 3
power-key IRQ to each controller.  Mainline RK3588 device trees currently omit
the PWM ``interrupts`` properties, while the Rockchip vendor DTS declares
them.  Continuous mode does not generate interrupts, so this model leaves the
GIC inputs disconnected; one-shot, capture, and power-key support must connect
them.

One-shot, capture, FIFO, DMA, power-key capture, center-aligned output and the
``ch_cnt_en`` control bit are not modeled yet.  Selecting the one-shot,
capture, or center-aligned modes, or setting ``ch_cnt_en``, is reported with
``LOG_UNIMP``.  The ``ch_cnt_en`` bit remains readable but a configuration with
it set does not generate a waveform.  For center-aligned output, the TRM
requires the effective period and duty to be even and ignores bit 0 during
waveform generation; the readback behavior of odd programmed values is not
specified.  The exact counter behavior of an enabled zero-period configuration
also remains unspecified.  IOC selection remains the responsibility of Issue
#163.

To run the PWM qtest:

.. code-block:: shell

   ninja tests/qtest/rk3588-pwm-test
   QTEST_QEMU_BINARY=./qemu-system-aarch64 ./tests/qtest/rk3588-pwm-test

The qtest covers all 10 unique controller channels routed to the 40-pin
header, the 50 us/20 kHz on-board fan channel, runtime polarity updates, both
input clock roots, a divided clock whose frequency is not an integer number of
Hz, non-divisible period rounding, all 16 channel reset registers, and the 16
reset output levels.  Migration is checked while a channel is running by
verifying its register state, counter phase, output level and next waveform
edge on the destination.

The watchdog and the non-secure timer also exist per domain (``wdt-pmu`` at
``0xfd8e0000``, ``wdt-npu`` at ``0xfdaf8000``, ``timer-npu`` at
``0xfdb00000``); none of them is modeled.

All 40-pin header GPIOs are 3.3 V (3.63 V maximum); the SARADC inputs on the
header are 1.8 V (1.98 V maximum) and are not 5 V tolerant.  A pin carries one
function at a time, so the mux names listed for a pin are mutually exclusive,
and so are the pin groups of one controller.  Beyond the shared I2C0 and I2C1
buses, the header pairs that need a decision are SPI0 with UART4 on 19/23,
SPI1 with UART7 on 7/11/15/32, PWM with UART2 on 36/38 and PWM with UART3 on
12/35.

Verification
^^^^^^^^^^^^

The window map can be read back from the monitor: a modeled device appears
under its own name, while an unimplemented window appears as
``rk3588.<name>`` at a negative priority::

   (qemu) info mtree -f
   00000000feb40000-00000000feb4001f (prio 1, i/o): serial
   ...
   00000000fd890000-00000000fd89ffff (prio -1000, i/o): rk3588.uart0
   00000000fec80000-00000000fec8ffff (prio -1000, i/o): rk3588.i2c6

A guest access to one of those windows is reported with ``-d unimp`` and the
stub name, which is the quickest way to tell "not implemented yet" from "wrong
address"::

   rk3588.i2c6: unimplemented device write (size 4, offset 0x0000, value 0xdeadbeef)

The machine test covers the modeled side of the map::

   $ QTEST_QEMU_BINARY=./qemu-system-aarch64 ./tests/qtest/rock-5b-test
   ok 1 /aarch64/rock-5b/machine-topology
   ok 2 /aarch64/rock-5b/pcie-rtl8125
   ok 3 /aarch64/rock-5b/sdmmc
   ok 4 /aarch64/rock-5b/cru
   ok 5 /aarch64/rock-5b/sdmmc-idmac
   ok 6 /aarch64/rock-5b/uart2-chardev
   ok 7 /aarch64/rock-5b/uart2-rx-fifo-irq
   ok 8 /aarch64/rock-5b/uart3-isolation

The UART tests attach socket character backends to the documented
``-serial`` slots: slot 1 for UART2 and slot 3 for UART3.  They check UART2
transmit and receive bytes, FIFO enable and receive-ready status, the
four-byte receive interrupt threshold, IRQ masking and re-enabling,
clearing pending data, and reset.  The UART3 test checks that its registers
and character backend remain independent of UART2.

For the serial console, the slot assignment above is what makes
``-serial null -serial mon:stdio`` print the UART2 console: an image that
writes to UART2 shows up on the second ``-serial`` option, while one that
writes to UART1 needs a third one.

Boot options
~~~~~~~~~~~~

The ``rock-5b`` machine boots U-Boot proper when ``-bios`` is given and
Linux directly when ``-kernel`` is given; one of the two is required.
Both methods start the primary CPU in non-secure EL2 and provide PSCI
through SMC calls. DRAM and clocks are assumed to be initialized;
BootROM, DDR training firmware, SPL and BL31 are not modeled.

U-Boot proper is supplied as a raw binary with ``-bios``. QEMU loads it
at ``0x00200000``, so it must be linked for that address. The device tree
is taken from the Linux FIT image loaded by U-Boot, so ``-dtb`` cannot be
used with this method.

By default RAM above the 4 GiB peripheral hole is mapped at
``0x100000000``, matching the reference U-Boot/Linux image set. Some
downstream firmware requires that bank at ``0x400000000`` and selects it
with ``-machine rock-5b,high-ram-base=0x400000000``. The property may be
used with either boot method.

Direct Linux boot supplies an AArch64 Linux ``Image`` with ``-kernel``
and a device tree with ``-dtb``; ``-initrd`` and ``-append`` are optional.
QEMU does not generate a device tree for this machine.

Running
~~~~~~~

Serial ports are assigned as follows:

* ``-serial`` slot 0: the Type-C USB CDC console implemented by the DWC3
  device-mode controller.
* ``-serial`` slot 1: UART2, the debug console on the board header and the
  console used by U-Boot and Linux.
* further ``-serial`` options connect to UART1 and UART3 through UART9 in
  that order.

Because UART2 is on slot 1, a Linux or U-Boot console on stdio is selected
with ``-serial null -serial mon:stdio``. The USB CDC console can be attached
to a host socket with a separate character backend, for example
``-chardev socket,id=usbcon,path=/tmp/rock5b-usb-cdc.sock,server=on,wait=off
-serial chardev:usbcon``; the host side is then a plain serial port over the
emulated Type-C connection.

U-Boot proper boot
^^^^^^^^^^^^^^^^^^

With ``u-boot-dtb.bin`` and ``spi-nor.img``:

.. code-block:: bash

   $ qemu-system-aarch64 \
       -machine rock-5b -m 2G -smp 8 \
       -display none -monitor none \
       -serial null -serial mon:stdio \
       -bios u-boot-dtb.bin \
       -drive if=mtd,index=0,file=spi-nor.img,format=raw

The SPI NOR image must be exactly 16 MiB. Add ``snapshot=on`` to the
drive option to discard guest writes.

Firmware boot from SD over the Type-C USB CDC console
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The machine boots firmware built for the real board with a U-Boot that can
read the board SD card layout: U-Boot scans the modeled ``dw_mmc``
controller, loads ``boot.scr``, stages the payloads in DRAM and enters the
firmware with ``bootm``. The firmware console then appears on the emulated
Type-C USB CDC port. An RTL8125 user-mode network is attached with ``-nic``
for its DHCP/network stack:

.. code-block:: bash

   $ qemu-system-aarch64 \
       -machine rock-5b,high-ram-base=0x400000000 -m 8G -smp 8 \
       -display none -monitor none \
       -chardev socket,id=usbcon,path=/tmp/rock5b-usb-cdc.sock,server=on,wait=off \
       -serial chardev:usbcon \
       -serial file:uboot-uart2.log \
       -bios u-boot-dtb.bin \
       -drive if=mtd,index=0,file=spi-nor-mmc.img,format=raw,snapshot=on \
       -drive if=sd,index=2,file=sd-payload.img,format=raw \
       -nic user,model=rtl8125

Connect the host side with ``socat - UNIX-CONNECT:/tmp/rock5b-usb-cdc.sock``
and wait for the firmware prompt.

Direct Linux boot
^^^^^^^^^^^^^^^^^

With ``Image``, ``rootfs.cpio.gz`` and ``rk3588-rock-5b.dtb``:

.. code-block:: bash

   $ qemu-system-aarch64 \
       -machine rock-5b -m 2G -smp 8 \
       -display none -monitor none \
       -serial null -serial mon:stdio \
       -kernel Image -initrd rootfs.cpio.gz -dtb rk3588-rock-5b.dtb \
       -append "console=ttyS2,1500000n8 rdinit=/init"

Limitations
~~~~~~~~~~~

The machine is TCG-only; KVM is not supported. BootROM, DDR training,
SPL and BL31 are not modeled; firmware boot starts U-Boot proper directly.
The remaining RK3588 peripherals are unimplemented. Some downstream
firmware requires the ``high-ram-base=0x400000000`` option because its
fixed guest windows are tied to that physical RAM bank. The SD controller
supports one card on ``if=sd,index=2`` and the RTL8125 has no PHY/MAC
calibration data (link state and packet path are modeled, the PHY data
values are synthetic). The modeled DWC3 CDC console buffers transmit data
across host connection establishment and paces console input so that the
firmware's line-coding control bridge does not coalesce characters; under
heavy host CPU oversubscription the guest can still log rare endpoint-command
deadline warnings. Migration and VM snapshots are unsupported.

ROCK 5B+
--------

The ``rock-5b-plus`` machine models the Radxa ROCK 5B+ single-board
computer: LPDDR5, the two board PCIe hosts, and the firmware compatibility
profile needed by Radxa's RK3588 SDK image.  With separate board media,
firmware boot reads SPI NOR from ``if=mtd,index=0`` and reads the SD payload
media from ``if=sd,index=2`` (the controller selected by U-Boot's
``mmc dev 1``).  A complete legacy Radxa image at ``if=sd,index=0`` remains
accepted when no SPI drive is supplied.

The machine is still built on the legacy monolithic RK3588 machine base and
shares the legacy device models with the boards described below.  Its
board-specific firmware layout follows.

Radxa ROCK 5B+ Firmware Image
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The ``rock-5b-plus`` firmware profile accepts either a complete raw Radxa SDK
image or the split layout used by the real board: SPI NOR contains U-Boot and
the SD card contains the firmware and guest payload files.  The split layout keeps
the firmware and payload media separate while preserving the board's boot
order.

For a complete legacy image, no extraction or repackaging is required:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rock-5b-plus \
       -smp 1 \
       -m 8G \
       -drive if=sd,index=0,file=rock-5b-plus_bookworm_kde_b2.output.img,format=raw \
       -snapshot \
       -serial mon:stdio \
       -display none

For the split SPI/SD layout, pass a 16 MiB SPI NOR image containing the
Rockchip SPI boot image and an SD image whose FAT partition contains the files
loaded by the U-Boot environment (the firmware image, its device tree,
``zephyr-guest.bin``, ``linux-Image.flash.gz``, and
``initramfs.cpio.flash.gz``):

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg,thread=multi \
       -machine rock-5b-plus \
       -smp 8 \
       -m 8G \
       -drive if=mtd,index=0,file=rock5b-spi-16m.img,format=raw \
       -drive if=sd,index=2,file=rock5b-sd-payload.img,format=raw \
       -serial mon:stdio \
       -monitor none \
       -display none

The SPI image has the RKNS header at offset ``0x8000`` and the FIT at
``0x60000``.  The SD payload image is attached to the DesignWare MMC
controller, so U-Boot sees it as ``mmc 1`` and uses ``mmc 1:1`` for FAT loads.
The RK3588 machines default to 8 GiB.  ROCK 5B+ uses the direct-kernel
RAM base at ``0x10000000`` by default.  RAM below the 4 GiB peripheral window
is mapped in the low bank; the remaining RAM is mapped at 16 GiB so it does
not overlap the fixed reserved high-memory window at 4 GiB.

This path runs the image's DDR/TPL and SPL code, verifies all FIT loadables,
uses the FIT metadata to select the U-Boot load address dynamically, enters
U-Boot proper, and continues through its ``extlinux`` boot flow.  U-Boot loads
the SDK kernel, initramfs, and
``rk3588-rock-5b-plus.dtb`` from the image root file system before printing
``Starting kernel ...``.

The ``firmware-bootargs`` machine property appends parameters to the kernel
command line without touching the image: U-Boot ``booti`` rewrites
``/chosen/bootargs`` from its own environment immediately before entering the
kernel, so the model keeps the DTB bootargs value patched in place (a
same-length store in the existing property slot; the trailing
``androidboot.fwver`` marker is dropped to make room) until the kernel entry
is observed, then leaves the tree untouched.  The Radxa Bookworm image boots
headless with the parameters above; without them the KDE graphical target
stalls (no DRM) and the PSCI cpuidle path can leave the CPU asleep.

The verified run reaches the ``rock-5b-plus login:`` prompt on the serial
console (user ``rock`` / ``rock``) with the official 6.1.84-8-rk2410 kernel.
Inside the guest the SD card appears as ``mmcblk0`` with the ``/config``,
``/boot/efi``, and root partitions; ``/proc/mtd`` shows the 16 MiB SFC flash
as ``mtd0`` (``loader`` partition); and ``lspci`` enumerates the PCIe root
bridge (``0002:20:00.0 DWC_usb3 / PCIe bridge``).

A network endpoint on ``pcie2x1l0`` is verified both ways.  The qtest
``/rock-5b-plus/pcie2x1l0-virtio-net`` attaches ``virtio-net-pci`` to the root
bridge secondary bus (``bus=/pcie2x1l0/pcie/designware-pcie-root/dw-pcie``)
and exercises the ATU config path, BAR assignment, MSI-X table, and full
RX/TX over a socket ``-netdev``.  In the real Linux guest, attaching a NIC on
the same bus works end to end::

   $ qemu-system-aarch64 -machine rock-5b-plus,firmware-bootargs='cpuidle.off=1 systemd.unit=multi-user.target' \
       -smp 1 -m 8G -drive if=sd,index=0,file=rock-5b-plus_bookworm_kde_r7.output_512.img,format=raw -snapshot \
       -netdev user,id=n0 -device e1000e,bus=/pcie2x1l0/pcie/designware-pcie-root/dw-pcie,netdev=n0 \
       -serial mon:stdio -display none

The guest kernel enumerates the endpoint on the bridge secondary bus
(``0002:21:00.0``), assigns BARs through the bridge windows (32-bit at
0xf2xxxxxx and a 64-bit prefetch BAR above 4 GiB), and the e1000e driver comes
up at 1 Gbit/s with DHCP (10.0.2.15) and working ping/HTTP through
``-netdev user``.  (The stock Radxa kernel does not ship virtio PCI drivers;
the image-shipped e1000e driver is used for the real-boot check.)

Legacy RK3588 board machines
----------------------------

The RK3588 machines are local downstream models for booting Linux and firmware
images built for Rockchip RK3588 boards.  They support QEMU's direct Arm Linux
boot path and a downstream firmware path that runs the Rockchip TPL/SPL image,
validates the U-Boot FIT loadables, hands off to U-Boot proper, and lets
U-Boot boot Linux or firmware test images from modeled MMC media.

Two legacy board machines are available.  Each board has its own machine source
file and build-time Kconfig entry; the common ``rk3588`` type is abstract and
contains only shared SoC construction and boot orchestration:

``rk3588-evb``
  Rockchip RK3588 EVB-style board.  Firmware boot reads the Rockchip RKNS
  image from ``if=sd,index=0`` and exposes it as the non-removable eMMC
  controller.

``rk3588s-roc-pc``
  Firefly ROC-RK3588S-PC board, exposed by QEMU as ``rk3588s-roc-pc`` and
  using the hardware compatible ``rockchip,rk3588s-firefly-roc-pc``.
  Firmware boot reads the Rockchip RKNS image from ``if=sd,index=2`` and
  exposes it through the SDMMC/TF-card controller used by the package's
  ``mmc dev 1`` boot script.  This machine maps the fixed reserved guest/shared
  RAM windows by default, corresponding to the real board's larger DRAM layout.

Supported devices
~~~~~~~~~~~~~~~~~

The machines currently model or stub the devices needed by the downstream
RK3588 kernel and firmware smoke tests:

* 8 Arm cores matching the RK3588 big.LITTLE layout: Cortex-A55 CPUs 0-3 and
  Cortex-A76 CPUs 4-7.  Under TCG the CPU objects expose EL2 and EL3 for the
  firmware paths.  The RK3588 machines do not install RK3588-only CPU
  compatibility properties for EL2 FP/SIMD traps or EL2 PAN handling.
* GICv3 with two ITS blocks and LPI support.
* All ten RK3588 UARTs (UART0-UART9) through QEMU's ``serial_mm``
  16550-compatible model, each with a DesignWare APB UART vendor
  register cover (USR @0x7c).  Only the ports with I/O routed out on
  the ROCK 5B+ (UART1, UART2, UART3, UART4, UART7) bind a serial
  chardev: UART2 keeps ``serial_hd(0)`` as the console, the others
  map to ``-serial`` slots 1..4 in table order.  The remaining
  ports (UART0, UART5, UART6, UART8, UART9) are modeled without
  external output.
* GPIO0 through GPIO4 through the Rockchip GPIO v2 bank model.
* Dedicated RK3588 PMU0/PMU1/SYS GRF banks, plus reusable Rockchip RAM-backed
  syscon blocks for IOC and firewall-style register banks.
* Dedicated RK3588 DDR controller/PHY windows and the BL31 DDR runtime
  descriptor used by the vendor firmware.
* Rockchip secure timer stub.
* RK3588 CRU and SCMI-over-SMC clock/reset support.
* SDHCI eMMC and Synopsys DesignWare MMC for the SD-card controller.
* RK3588 SFC with an XTX XT25F128 SPI NOR device on chip select 0.
* Synopsys DWMAC4 GMAC0 and GMAC1.
* Rockchip DesignWare PCIe host wrapper, including MSI/MSI-X through GIC ITS.
* Firmware-only USB2 EHCI/OHCI register windows used by U-Boot bootflow
  scanning.
* Optional RK3588 RKNN/RKNPU core register model, enabled with
  ``-machine ...,rknpu=on``.  This exposes the three RK3588 RKNN cores and
  implements hardware-pipeline execution for register-level jobs submitted
  through the Linux mainline ``rocket`` or vendor ``rknpu`` driver.

The SFC model is the register-driven SPI-memory controller used by the
Rockchip Linux and U-Boot drivers.  It supports JEDEC/SFDP discovery, PIO
transfers, and DMA transfers.  ``SPI`` in the RK3588 machine source also names
GIC Shared Peripheral Interrupt numbers; it is not a second SPI controller.

The optional RKNPU model exposes the three accelerator cores and their
Rockchip IOMMU.  It is enabled with ``-machine ...,rknpu=on``.  The selected
machine type determines the guest-visible binding: ``rk3588-evb`` and
``rock-5b-plus`` use the aggregate binding expected by the vendor ``rknpu``
driver, while ``rk3588s-roc-pc`` exposes the per-core binding used by the
mainline ``rocket`` driver.

Jobs may be submitted through PC-fetched command descriptors or slave-mode
register banks.  PC descriptors inherit register values not rewritten by a
later sparse descriptor.  The banked register state and any in-flight task are
included in migration state.  The IOMMU implements the mapping, invalidation,
translation, and permission-fault behavior required by both drivers.

The functional backend is register-driven and does not identify model names,
task numbers, or fixed tensor shapes.  The implemented subset covers INT8 and
FP16 CNA/CORE/DPU pipelines for matrix multiplication and direct or depthwise
convolution, DPU-RDMA data movement and arithmetic, conversion and LUT stages,
and PPU identity and max-pooling operations.  Tensor dimensions, strides,
valid and storage channels, layouts, and DMA addresses are decoded from the
submitted register state.

The model has been exercised with unmodified ``rocket`` and vendor ``rknpu``
drivers and with RKNN Runtime workloads.  This validates the implemented
formats and stage combinations, but does not imply complete RK3588 NPU or
model coverage.  Unsupported active controls and layouts fail explicitly
rather than being interpreted as a known workload profile.  Host-memory and
work limits bound functional execution so malformed guest jobs cannot block or
exhaust QEMU.

Common IP boundaries
~~~~~~~~~~~~~~~~~~~~

Several blocks are modeled as Rockchip- or DesignWare-style reusable IP, rather
than as RK3588-only devices:

* ``rockchip-syscon`` covers RAM-backed GRF/IOC/firewall register banks and
  implements Rockchip HIWORD writes.
* ``rockchip-stimer`` covers the secure timer register layout used by Rockchip
  firmware.
* ``rk3588-pwm`` covers the four-channel RK3588 PWM register block and its
  continuous left-aligned digital outputs.
* ``dw-apb-uart-vendor`` covers the Synopsys DesignWare APB UART extension
  window above the 16550-compatible core.  The UART core itself is QEMU's
  reusable ``serial_mm`` 16550-compatible model.
* ``rockchip-dwcmshc-vendor`` covers the Rockchip vendor window above the
  SDHCI core for DWCMSHC eMMC controllers.  The SDHCI SDMA buffer-boundary
  behavior is generic SDHCI logic, not RK3588-specific logic.
* ``dw-mmc`` covers the Synopsys DesignWare MMC register bank, PIO FIFO data
  ports, and IDMAC descriptor flow used by the RK3588 SD-card controller.
* ``rockchip-pcie-host`` wraps QEMU's DesignWare PCIe host and adds the
  Rockchip APB vendor window expected by the ``dw-rockchip`` Linux driver.
  Address mapping, compatible strings, MSI routing, and interrupt numbers stay
  in the RK3588 board code.

All MMIO register behavior is implemented outside the machine sources.  The
RK3588 CRU, GRF, DDR, ATF DDR runtime descriptor, firmware compatibility MMIO,
SCMI, secure OTP, and firmware USB2 host windows live in independently built
devices under the corresponding ``hw/*`` subsystem directories.  The common
machine source only maps and wires those devices and implements SoC boot-flow
orchestration such as BootROM loading, PSCI/GIC handoff, and the
SPL/BL31-to-U-Boot compatibility path.  The USB2 device is intentionally a
firmware-oriented register model; it supplies the reset-visible EHCI/OHCI state
U-Boot needs while scanning boot devices.

Direct Linux Boot
~~~~~~~~~~~~~~~~~

The following command boots the RK3588 Linux image and initramfs stored under
``build/agent`` on the EVB machine, and attaches the smoke-test eMMC image, the
board GMAC, and one PCIe virtio-net device:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb \
       -smp 2 \
       -m 1G \
       -kernel build/agent/linux-src/arch/arm64/boot/Image \
       -initrd build/agent/initramfs.cpio.gz \
       -append "console=ttyS2,1500000n8 rdinit=/init" \
       -drive if=sd,file=build/agent/rk3588-modeling/logs/emmc-smoke.img,format=raw \
       -nic user,model=gmac0 \
       -netdev user,id=vnet0 \
       -device virtio-net-pci,netdev=vnet0 \
       -serial mon:stdio \
       -display none

The kernel console is UART2, so keep ``console=ttyS2,1500000n8`` in the kernel
command line.

The ROC PC machine supports the same direct Linux boot path:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588s-roc-pc \
       -smp 2 \
       -m 1G \
       -kernel build/agent/linux-src/arch/arm64/boot/Image \
       -initrd build/agent/initramfs.cpio.gz \
       -append "console=ttyS2,1500000n8 rdinit=/init" \
       -drive if=sd,file=build/agent/rk3588-modeling/logs/emmc-smoke.img,format=raw \
       -nic user,model=gmac0 \
       -netdev user,id=vnet0 \
       -device virtio-net-pci,netdev=vnet0 \
       -serial mon:stdio \
       -display none

ROCK 5B+ supports the same path with a Radxa SDK kernel.  For example:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rock-5b-plus \
       -smp 8 \
       -m 1G \
       -kernel Image \
       -initrd initramfs.cpio.gz \
       -append "console=ttyS2,1500000n8 earlycon=uart8250,mmio32,0xfeb50000,1500000n8 keep_bootcon rdinit=/init" \
       -serial mon:stdio \
       -display none

Firmware U-Boot Boot
~~~~~~~~~~~~~~~~~~~~

The firmware path expects a raw eMMC image containing Rockchip's combined
``u-boot-rockchip.bin`` at LBA 64:

.. code-block:: bash

   $ truncate -s 64M build/agent/rk3588-firmware-boot/scratch/rk3588-firmware-emmc.img
   $ dd if=build/agent/rk3588-firmware-boot/scratch/u-boot-build/u-boot-rockchip.bin \
        of=build/agent/rk3588-firmware-boot/scratch/rk3588-firmware-emmc.img \
        bs=512 seek=64 conv=notrunc

Run the firmware smoke path with:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb \
       -smp 1 \
       -m 1G \
       -drive if=sd,index=0,file=build/agent/rk3588-firmware-boot/scratch/rk3588-firmware-emmc.img,format=raw \
       -serial mon:stdio \
       -display none

This path executes the Rockchip DDR/TPL image, enters U-Boot SPL, validates the
FIT loadables, and replaces SPL's final ATF branch with a QEMU-private SMC that
enters BL31 with SPL's BL31 parameter block.  BL31 runs through the modeled
initialization path; a narrow BL31 exit shim then hands off to U-Boot proper at
``0x800000`` with the EL2/GIC/PSCI state expected by the downstream smoke path.
After the handoff the model exposes the USB2 host register windows so U-Boot
bootflow probing can continue without taking a synchronous abort on unmapped
firmware MMIO.  It is intended for downstream firmware bring-up coverage, not
as a complete replacement for a real RK3588 PMU/secure firmware environment.

U-Boot to Linux Boot
~~~~~~~~~~~~~~~~~~~~

The complete U-Boot path uses a raw eMMC image that contains the Rockchip
firmware at LBA 64 and a boot partition with ``extlinux.conf``, ``Image``,
``initramfs.cpio.gz``, and a QEMU-generated RK3588 DTB.  The DTB embedded in
the image must be generated with the same ``-smp`` value used at runtime.

The locally verified downstream image boots with:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb \
       -smp 2 \
       -m 1G \
       -drive if=sd,index=0,file=build/agent/rk3588-uboot-linux/scratch/rk3588-uboot-linux-emmc-earlycon.img,format=raw \
       -nic user,model=gmac0 \
       -netdev user,id=vnet0 \
       -device virtio-net-pci,netdev=vnet0 \
       -serial mon:stdio \
       -display none

The verified ``extlinux.conf`` passes:

.. code-block:: text

   console=ttyS2,1500000n8 earlycon=uart8250,mmio32,0xfeb50000,1500000n8 keep_bootcon loglevel=8 rdinit=/init

U-Boot loads the kernel, initramfs, and DTB from eMMC, prints
``Starting kernel ...``, and the smoke initramfs reaches
``=== init done, exec sh ===``.
