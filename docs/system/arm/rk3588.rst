Rockchip RK3588 Boards
======================

The RK3588 machines are local downstream models for booting Linux and firmware
images built for Rockchip RK3588 boards.  They support QEMU's direct Arm Linux
boot path and a downstream firmware path that runs the Rockchip TPL/SPL image,
validates the U-Boot FIT loadables, hands off to U-Boot proper, and lets
U-Boot boot Linux or ZVM test images from modeled MMC media.

Three board machines are available.  Each board has its own machine source
file and build-time Kconfig entry; the common ``rk3588`` type is abstract and
contains only shared SoC construction and boot orchestration:

``rk3588-evb``
  Rockchip RK3588 EVB-style board.  Firmware boot reads the Rockchip RKNS
  image from ``if=sd,index=0`` and exposes it as the non-removable eMMC
  controller.

``rk3588s-roc-pc``
  Firefly ROC-RK3588S-PC board, exposed by QEMU as ``rk3588s-roc-pc`` and
  using the hardware compatible ``rockchip,rk3588s-firefly-roc-pc``.
  Firmware boot reads the Rockchip RKNS image from ``if=sd,index=2`` and
  exposes it through the SDMMC/TF-card controller used by the package's
  ``mmc dev 1`` boot script.  This machine maps the fixed ZVM guest/shared RAM
  windows by default, corresponding to the real board's larger DRAM layout.

``rock-5b-plus``
  Radxa ROCK 5B+ with LPDDR5, the two board PCIe hosts, and the firmware
  compatibility profile needed by Radxa's RK3588 SDK image.  Firmware boot
  reads the raw Radxa image from ``if=sd,index=0`` and exposes it through the
  non-removable eMMC controller.

Supported devices
-----------------

The machines currently model or stub the devices needed by the downstream
RK3588 kernel and ZVM smoke tests:

* 8 Arm cores matching the RK3588 big.LITTLE layout: Cortex-A55 CPUs 0-3 and
  Cortex-A76 CPUs 4-7.  Under TCG the CPU objects expose EL2 and EL3 for the
  firmware and ZVM paths.  The RK3588 machines do not install RK3588-only CPU
  compatibility properties for EL2 FP/SIMD traps or EL2 PAN handling.
* GICv3 with two ITS blocks and LPI support.
* UART2 through QEMU's ``serial_mm`` 16550-compatible model, plus a vendor
  register cover for the DesignWare APB UART window.
* Rockchip GPIO banks.
* Dedicated RK3588 PMU0/PMU1/SYS GRF banks, plus reusable Rockchip RAM-backed
  syscon blocks for IOC and firewall-style register banks.
* Dedicated RK3588 DDR controller/PHY windows and the BL31 DDR runtime
  descriptor used by the vendor firmware.
* Rockchip secure timer stub.
* RK3588 CRU and SCMI-over-SMC clock/reset support.
* SDHCI eMMC and Synopsys DesignWare MMC for the SD-card controller.
* Synopsys DWMAC4 GMAC0 and GMAC1.
* Rockchip DesignWare PCIe host wrapper, including MSI/MSI-X through GIC ITS.
* Firmware-only USB2 EHCI/OHCI register windows used by U-Boot bootflow
  scanning.
* Optional RK3588 RKNN/RKNPU core register model, enabled with
  ``-machine ...,rknpu=on``.  This exposes the three RK3588 RKNN cores and
  implements the Linux mainline ``rocket`` driver's register-level job
  submission path with fake completion interrupts.

The machine does not instantiate a SPI controller yet.  ``SPI`` in the RK3588
machine source refers to GIC Shared Peripheral Interrupt numbers.

The optional RKNPU model is not yet a complete neural-network accelerator
emulator.  Its control path includes a Rockchip IOMMU model so Linux can probe,
attach, map, zap, and report translation or permission faults through the open
``rocket`` driver and the vendor ``rknpu`` driver.  For debugging, trace events
can walk the RK3588 IOMMU v2 page tables, sample submitted register command
buffers, decode command prefixes, and report raw or unknown command words.

An experimental functional mode is available with
``-machine ...,rknpu=on,rknpu-functional=on``.  It routes PC-fetched commands
or slave-mode CNA/CORE/DPU MMIO writes into banked register files, then decodes
an immutable hardware-pipeline task.  Slave mode is selected with
``PC_BASE_ADDRESS.bit0`` and triggered through ``GLOBAL_OPERATION_ENABLE``.
PC task descriptors are incremental: register values in both hardware banks
persist after completion, so a later sparse descriptor inherits fields that it
does not rewrite.  Registers that have not yet been written read their hardware
reset value rather than making descriptor completeness an execution
requirement.  The persistent banks and the in-flight task snapshot are both
migration state.
Execution is selected from decoded register fields and active hardware stages;
the functional backend does not recognize model names, task numbers, or fixed
tensor shapes.  Captured model tasks are regression and differential vectors,
not execution allowlists.  A new workload using an implemented combination of
formats, layouts, and stages therefore follows the same data path without a
model-specific enablement change.
The implemented subset has been exercised through the unmodified vendor RKNN
Runtime with RK3588 MobileNet V1, YOLOv8, and YOLOv5 models.  Their final
classification or detection results match the corresponding board runs.  This
is workload evidence for the decoded formats, layouts, and stages, not a claim
that every RKNN model or RKNPU control combination is implemented.
The current integer backend executes signed INT8 CNA/MAC pipelines with
signed INT8 and INT32 DPU output.  It covers width-one Matmul-style surfaces,
two-dimensional 1x1 direct convolution with stride one and no padding, and
3x3 direct convolution with stride one or two and one-cell top/left padding.
The stride-one profile also covers the hardware-observed asymmetric case with
left/bottom padding but no top/right padding.
INT8 depthwise convolution is executed when CNA and DPU select convolution
mode 3 and CORE enables depthwise operation.  Compact weights use 64-channel
groups, with kernel-row, kernel-column, channel order inside each group, and
each output channel multiplies only the corresponding input channel.  CNA
``PAD_CON1`` supplies the input domain padding value; interleaved input
converts it through the per-channel CVT path before convolution.
The functional backend also executes the board-validated FP16 Matmul profile:
inputs and weights are FP16, accumulation is FP32, and DPU writeback is either
FP16 or FP32.  FP16 grouped weights use the hardware's 16-output-channel
groups, while tensor dimensions, strides, and channel validity remain
register-derived.  The current FP16 profile requires direct CNA/CORE/DPU
execution, bypassed BS/BN/EW stages, zero ``PAD_CON1``, and a destination
surface stride large enough for one complete surface.  For FP16
partial-channel output, ``OFFSET_PEND`` supplies the raw16 value for storage
lanes beyond ``OUTPUT_CHANNELS_VALID``; the same control remains unsupported
for other precisions.  Unsupported controls fail explicitly rather than
being silently ignored.
The FP16 compact profile selected by ``NONALIGN_DMA``, ``GROUP_LINE_OFF``,
and ``ARGB_IN=8`` reads the register-sized input atom and consumes contiguous
input tensor and output-major weights without synthetic 32-input or 16-output
grouping.  This also covers multi-surface channel reductions and broadcasts
with register-derived valid and storage channel counts.
``BS_OW_CFG=0x126`` writes its FP16 storage lanes contiguously when the
destination surface stride is zero.  This covers the board-validated 1x1
broadcast reduction while retaining register-derived tensor dimensions.
The DPU-only main-RDMA path also executes signed INT8 feature data to FP16
writeback.  It derives dimensions, valid and storage channels, source and
destination addresses, and destination surface stride from the DPU and
DPU-RDMA registers.  Source features use 16-channel INT8 atoms, destination
features use eight-channel FP16 atoms, conversion is round-to-nearest-even,
and destination padding lanes are zero.  BS, BN, EW, BRDMA, and ERDMA must be
bypassed for this mode; unsupported flying-mode, precision, converter,
padding, notch, and layout controls fail before DMA.
The same main-RDMA frontend executes a composable integer pipeline over
16-channel INT8 atoms.  The main input passes through decoded BS, bypassed BN,
optional ERDMA-backed EW addition, and ``OUT_CVT`` stages before saturating to
INT8.  Register operands, signed multiplier shifts, both EW converter orders,
EW truncation, output rounding, valid channels, and destination surfaces are
applied from their control fields; unsupported active sources and modes fail
before DMA.  Neutral controls reduce this path to an exact copy.  Source,
ERDMA, and destination may overlap because all inputs are read before
writeback.  Storage lanes beyond ``OUTPUT_CHANNELS_VALID`` are cleared.
The main-RDMA frontend also implements the board-validated INT16 unpool mode.
For ``SRC_DMA_CFG=0x1249``, each eight-lane INT16 source atom is preserved as
its 16 raw little-endian bytes, exposed as one 16-lane INT8 output atom, and
repeated twice in both spatial directions.  All decoded input surfaces are
consumed and written as consecutive output surfaces.  Tensor dimensions,
channel counts, surface count, and DMA addresses remain register-derived;
unsupported unpool, padding, notch, stage, or conversion controls fail before
DMA.
The main-RDMA FP16 pipeline composes decoded BS and EW stages in hardware
order.  BS can add the FP32 ``BS_ALU_CFG`` operand and multiply by the FP16
operand in ``BS_MUL_CFG``; EW can independently bypass or consume an ERDMA
FP16 surface for subtraction or division.  Intermediate values remain FP32
through active stages and convert once to FP16 at writeback.  BS, ALU, MUL,
BN, and EW bypass bits are stage semantics rather than complete-register
profile signatures.  Unsupported source, truncate, shift, ReLU, converter,
and RDMA layout controls fail before DMA.  Input and output dimensions,
storage channels, valid channels, surface stride, and IOVA addresses are
derived from registers and bounded by the functional backend's resource
limits.  ``CORE.QUANTIFY`` and BS operand-source controls do not alter FP16
execution while the BS stage is bypassed.
The DPU-RDMA FP16 LUT profile is also register-driven.  It accepts FP16 input
surfaces, applies the decoded BN FP16 multiplier and FP32 add operand, selects
the LE or LO table using the configured LUT boundaries and five-bit index
fraction, performs rounded adjacent-entry interpolation, and converts the
result using ``OUT_CVT`` ``minus_exp`` before FP16 writeback.  The validated
profile includes the board-observed LE underflow clamp and table-specific
rounding: LE interpolation truncates before applying its output offset, while
LO interpolation rounds upward without that offset.  Its LUT road, slope,
precision, and stage controls
are capability-checked; unsupported combinations fail before DMA rather than
being treated as this profile.  Tensor dimensions and valid/storage channels
remain register-derived: all valid FP16 lanes are converted, including the
board-observed 1,008-lane softmax stage, while non-valid storage tail lanes
are written as zero.
The standalone raw16 tail profile preserves its one valid FP16 lane and fills
the other seven storage lanes with the 16-bit ``DPU_OFFSET_PEND`` value, as
used by the MobileNet softmax prelude.
The DPU-RDMA FP16 min/max profile scans all storage channels, including
partial-channel padding lanes.  ``MINMAX_CTL`` selects the global minimum or
maximum; when probability-only mode is clear, the second raw16 result word is
the first matching storage-lane index.  The result is written to the decoded
``DST_BASE_ADDR``.  Remaining auxiliary result words are not assigned stable
semantics because board captures show submit-context-dependent values.
The standalone FP16 EW profile consumes the decoded ERDMA FP16 operand and
performs the board-validated subtract or divide-and-convert operation.  Its EW
algorithm, per-lane ERDMA operand tensor, data format, source layout, and
output stride are capability-checked; mutations of those controls fail before
output DMA.
The modeled data path includes CORE round-to-nearest-even truncate, immediate
DPU BS/BN/EW add and multiply, BS subtract and ReLU, and the integer DPU output
converter's two add/multiply orderings, signed offset, scale, shift, rounding,
and signed INT32 saturation path.  BS and BN multiplication use independent
nonnegative and negative-result shifts with round-to-nearest-even.  BS, BN,
and EW stage results also saturate to signed INT32, and EW immediate
multiplication uses a signed 16-bit operand.  EW add and multiply apply
independent nonnegative and negative-result truncate fields with
round-to-nearest-even; EW bypass ignores those fields.  The OUT_CVT
``minus_exp`` field is accepted and has no
effect in the hardware-validated INT32 output mode.  These stages can be
composed in hardware order.  ``MC_SURF_OUT`` scatters at most eight 32-value
output blocks using the hardware-observed ``SURFACE_ADD`` layout.  Blocks
advance through flattened two-dimensional spatial positions before the next
32-channel group; unwritten holes remain untouched and overlapping block
addresses are written in task order.  External/RDMA operands are functionally executed for the first
per-pixel signed INT8 profile.  It supports EW add and multiply, plus the EW
operand converter's signed offset, unsigned scale, six-bit shift, and both
round-to-nearest-even and ties-away-from-zero modes.  Operand conversion runs
before EW arithmetic; the existing EW truncate and output-conversion stages
follow it.  Hardware-observed 16-channel source and EW surfaces across
multiple 32-channel groups, including notch progression, are read through
the modeled IOMMU.  The
validated BRDMA profile reads one signed INT32 BS add operand per output
channel across multiple 32-channel groups and broadcasts it across spatial
positions before BN and EW.  Its convolution weight is the signed packed
weight plus ``BS_OW_OP``; ``BS_OW_OP`` is not a post-accumulation divisor.
Compact input and output tails use the exact decoded weight byte count rather
than a rounded host-side allocation.  Compact FP16 output is contiguous; the
ordinary multi-surface stride field does not alter that compact layout.
Compact FP16 weights and output can be combined with ordinary planar input;
input feature layout is decoded independently from weight/output layout.
BS/BN RELUX are functionally modeled when their respective ``*_RELUX_EN``
bit is set, using the signed INT32 clamp interval ``[0, *_RELUX_CMP_VALUE]``.
EW RELUX is modeled for the validated ``0x20580`` immediate-add configuration
with a zero operand and the operand converter bypassed; the EW stage itself is
enabled.
BS/BN PRELU are modeled for their validated immediate multiply configurations:
the positive path is unchanged while the negative path uses the stage factor
and shift.  EW PRELU is modeled for the validated ``0x3a4`` immediate
multiply configuration, using the EW operand as the negative factor.  LUT
storage models the two hardware-observed 513-entry tables.  Writes with
``LUT_ACCESS_TYPE=1`` select a table through ``LUT_TABLE_ID`` and
auto-increment the 10-bit entry address.  Functional execution covers the
board-validated ``EW_CFG=0x302``, ``LUT_CFG=0x68``, ``LUT_INFO=0x50500``
profile with LE/LO endpoints and direct table interpolation; a constant-table
case and unique-entry positive/negative cases are differential-tested against
RK3588 hardware.  Negative inputs select LE (table 0) and nonnegative inputs
select LO (table 1); within the observed endpoints, the index is the
floor-divided input offset at 32 units per entry, with out-of-range values
clamped to entry 0 or 512 when the corresponding slope is zero.  The vendor
LO overflow profile is also modeled: ``LO_SLOPE_SCALE=0x40320000`` encodes
overflow scale ``0x4032``, and ``LO_SLOPE_SHIFT=0x1a0`` encodes shift 13.
Values above ``LO_END`` add the truncated product
``((input - LO_END) * 0x4032) >> 13`` to table 1 entry 512.  Other slope
profiles and general Sigmoid/Tanh profiles are not modeled yet.  Other
external operand formats and floating-point output converter modes outside the
FP16/FP32 writeback profile are not generally functionally executed yet.
The executor derives tensor dimensions, strides, channel validity, and output
layout from each submitted register file.  Hardware captures validate
arithmetic and layout; they are not a whitelist of shapes or model tasks.
The CNA input path supports the board-validated interleaved RGB888 mode with
``NONALIGN_DMA`` and ``GROUP_LINE_OFF`` enabled.  Per-channel CVT offset,
scale, truncation, rounding, and signed-input selection are applied before
convolution.  The validated MobileNet input profile converts unsigned bytes
with ``(input - 128) * 16384 >> 14``.  Its 16-channel weight atom, complete
QD convolution-window sum, stride, padding, and right-edge clipping are
derived from the submitted registers; output surfaces use the programmed DPU
surface stride.
The validated spatial EW DPU-RDMA profile uses the same 16-channel operand
planes with output-space surface stride/notch.  Spatial BRDMA reads one
signed INT32 bias per channel and broadcasts it across the output surface.
The mode uses the
modeled RK3588 IOMMU page tables, including paging state and PTE read/write
permissions, to read commands, input, and weights and writes the NPU-layout
output before raising
the normal completion interrupt.  DMA mapping failures follow the modeled
IOMMU and stage status behavior.  Operator controls that are not implemented
yet are reported as explicit execution capability errors rather than being
treated as model or shape restrictions.  Functional execution defaults to
QEMU host-safety ceilings of 256 MiB of aggregate temporary buffers,
``2^28`` MAC operations or element conversions per DPU task, and ``2^24``
work items per PPU task.
These are implementation safety boundaries rather than RK3588 shape limits;
tasks exceeding them fail before allocation or DMA.  PC mode streams
sequential task chains through one pending task snapshot and schedules one
logical task per timer callback, including for the full 12-bit task-count
field.  The captured MobileNet
submission contains 120 logical descriptors that reuse 107 immutable command
payloads behind three PC roots of 50, 34, and 23 payloads.  Slave mode
supports one directly configured task and reports its hardware-observed task
status.  The property is off by default; when it is off the model performs no
functional DMA reads or writes.  Other DPU-RDMA data modes, precisions, and
notch layouts, as well as
other PPU execution modes and cycle timing remain unimplemented.  The current
PPU/RDMA executor handles signed INT8 identity and max-pooling semantics with
per-surface DMA, row stride, padding, and channel-surface iteration.  Max
pooling compares complete signed bytes and copies the first winning byte.
Identity execution copies all 32 bytes without arithmetic.  The PPU and
PPU-RDMA windows expose their
``S_STATUS`` and ``S_POINTER`` registers.  Successful standalone completion
reports task status ``0xf000``, raw stage status ``0xc0000000``, and the
pointer-selected ``0x400`` or ``0x800`` low completion bit; those low bits are
independently cleared through PC ``INT_CLEAR``.  PPU-to-DPU chains retain the
PPU stage status while the final DPU owns the normal job completion interrupt.
Successful execution reports PPU/PPU-RDMA status ``0xc`` on the captured bank;
the tested IOMMU translation or permission faults report ``0x5``, abort DMA,
and do not add generic PC DMA read/write status bits.

By default, ``rknpu=on`` exposes three independent
``rockchip,rk3588-rknn-core`` device-tree nodes for the mainline Rocket driver.
Adding ``rknpu-vendor-fdt=on`` instead exposes the same modeled MMIO and IRQ
resources through the aggregate ``rockchip,rk3588-rknpu`` node and four-window
``rockchip,iommu-v2`` node used by the Rockchip vendor driver.  This option
changes only the generated guest binding; it does not add a second accelerator
or alter register behavior.

The decoder keeps software-visible valid and storage dimensions separate.
For the current INT8 path, CNA ``DATA_SIZE1`` supplies valid and storage input
channels, CNA ``WEIGHT_SIZE2`` supplies weight kernels, and DPU
``DATA_CUBE_CHANNEL`` supplies original and cube output channels.  CORE and
DPU WDMA channel, width, and height fields are checked against the cube size.
The DPU ``DATA_CUBE_HEIGHT.MINMAX_CTL`` field is decoded and non-zero values
are reported as unsupported until min/max output semantics are modeled.
The INT8 QD BRDMA path additionally requires the board-validated external
CPEND operand selection (``BS_OW_CFG=0x125`` for ordinary convolution and
``0x36d`` for depthwise, with ``BS_OW_OP=0``); the corresponding BRDMA feature
modes are ``0x7810`` and ``0x7816``.  Other CPEND operand and bypass modes are
reported as unsupported until their semantics are modeled.  Hardware-level
shape checks use the documented register
relationships.  The direct INT32 executor uses a four-channel storage atom.
The depthwise INT32 path derives its channel-plane width and rows per surface
from the DPU cube channels, valid channels, output atom, and ``SURFACE_ADD``;
inactive lanes in each physical plane are cleared.  Other DPU output layouts
remain under implementation.  Partial valid/storage and valid/cube
submissions are decoded using their register-provided packed layout; the
partial-channel qtest verifies that valid lanes execute while padding lanes
remain zero.  These implementation details are not hardware shape
restrictions.  In particular, hardware captures with ``M=2``,
``M=3``, and ``M=5`` prove that M need not be a multiple of four.
The qtest suite directly replays and byte-compares the smallest captured
``M=1,K=64,N=32`` vector in
``tests/data/rk3588-rknpu-matmul-int8-m1-k64-n32``; its provenance and input,
weight, command, and output checksums are recorded alongside the files.

Common IP boundaries
--------------------

Several blocks are modeled as Rockchip- or DesignWare-style reusable IP, rather
than as RK3588-only devices:

* ``rockchip-syscon`` covers RAM-backed GRF/IOC/firewall register banks and
  implements Rockchip HIWORD writes.
* ``rockchip-stimer`` covers the secure timer register layout used by Rockchip
  firmware.
* ``dw-apb-uart-vendor`` covers the Synopsys DesignWare APB UART extension
  window above the 16550-compatible core.  The UART core itself is QEMU's
  reusable ``serial_mm`` 16550-compatible model.
* ``rockchip-dwcmshc-vendor`` covers the Rockchip vendor window above the
  SDHCI core for DWCMSHC eMMC controllers.  The SDHCI SDMA buffer-boundary
  behavior is generic SDHCI logic, not RK3588-specific logic.
* ``dw-mmc`` covers the Synopsys DesignWare MMC register bank, PIO FIFO data
  ports, and IDMAC descriptor flow used by the RK3588 SD-card controller.
* ``rockchip-pcie-host`` wraps QEMU's DesignWare PCIe host and adds the
  Rockchip APB vendor window expected by the ``dw-rockchip`` Linux driver.
  Address mapping, compatible strings, MSI routing, and interrupt numbers stay
  in the RK3588 board code.

All MMIO register behavior is implemented outside the machine sources.  The
RK3588 CRU, GRF, DDR, ATF DDR runtime descriptor, firmware compatibility MMIO,
SCMI, secure OTP, and firmware USB2 host windows live in independently built
devices under the corresponding ``hw/*`` subsystem directories.  The common
machine source only maps and wires those devices and implements SoC boot-flow
orchestration such as BootROM loading, PSCI/GIC handoff, and the
SPL/BL31-to-U-Boot compatibility path.  The USB2 device is intentionally a
firmware-oriented register model; it supplies the reset-visible EHCI/OHCI state
U-Boot needs while scanning boot devices.

Direct Linux Boot
-----------------

The following command boots the RK3588 Linux image and initramfs stored under
``build/agent`` on the EVB machine, and attaches the smoke-test eMMC image, the
board GMAC, and one PCIe virtio-net device:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb \
       -smp 2 \
       -m 1G \
       -kernel build/agent/linux-src/arch/arm64/boot/Image \
       -initrd build/agent/initramfs.cpio.gz \
       -append "console=ttyS2,1500000n8 rdinit=/init" \
       -drive if=sd,file=build/agent/rk3588-modeling/logs/emmc-smoke.img,format=raw \
       -nic user,model=gmac0 \
       -netdev user,id=vnet0 \
       -device virtio-net-pci,netdev=vnet0 \
       -serial mon:stdio \
       -display none

The kernel console is UART2, so keep ``console=ttyS2,1500000n8`` in the kernel
command line.

The ROC PC machine supports the same direct Linux boot path:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588s-roc-pc \
       -smp 2 \
       -m 1G \
       -kernel build/agent/linux-src/arch/arm64/boot/Image \
       -initrd build/agent/initramfs.cpio.gz \
       -append "console=ttyS2,1500000n8 rdinit=/init" \
       -drive if=sd,file=build/agent/rk3588-modeling/logs/emmc-smoke.img,format=raw \
       -nic user,model=gmac0 \
       -netdev user,id=vnet0 \
       -device virtio-net-pci,netdev=vnet0 \
       -serial mon:stdio \
       -display none

ROCK 5B+ supports the same path with a Radxa SDK kernel.  For example:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rock-5b-plus \
       -smp 8 \
       -m 1G \
       -kernel Image \
       -initrd initramfs.cpio.gz \
       -append "console=ttyS2,1500000n8 earlycon=uart8250,mmio32,0xfeb50000,1500000n8 keep_bootcon rdinit=/init" \
       -serial mon:stdio \
       -display none

Firmware U-Boot Boot
--------------------

The firmware path expects a raw eMMC image containing Rockchip's combined
``u-boot-rockchip.bin`` at LBA 64:

.. code-block:: bash

   $ truncate -s 64M build/agent/rk3588-firmware-boot/scratch/rk3588-firmware-emmc.img
   $ dd if=build/agent/rk3588-firmware-boot/scratch/u-boot-build/u-boot-rockchip.bin \
        of=build/agent/rk3588-firmware-boot/scratch/rk3588-firmware-emmc.img \
        bs=512 seek=64 conv=notrunc

Run the firmware smoke path with:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb \
       -smp 1 \
       -m 1G \
       -drive if=sd,index=0,file=build/agent/rk3588-firmware-boot/scratch/rk3588-firmware-emmc.img,format=raw \
       -serial mon:stdio \
       -display none

This path executes the Rockchip DDR/TPL image, enters U-Boot SPL, validates the
FIT loadables, and replaces SPL's final ATF branch with a QEMU-private SMC that
enters BL31 with SPL's BL31 parameter block.  BL31 runs through the modeled
initialization path; a narrow BL31 exit shim then hands off to U-Boot proper at
``0x800000`` with the EL2/GIC/PSCI state expected by the downstream smoke path.
After the handoff the model exposes the USB2 host register windows so U-Boot
bootflow probing can continue without taking a synchronous abort on unmapped
firmware MMIO.  It is intended for downstream firmware bring-up coverage, not
as a complete replacement for a real RK3588 PMU/secure firmware environment.

Radxa ROCK 5B+ Firmware Image
-----------------------------

The ``rock-5b-plus`` firmware profile also accepts a complete raw image made by
the Radxa RK3588 SDK.  No extraction or repackaging is required:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rock-5b-plus \
       -smp 1 \
       -m 2G \
       -drive if=sd,index=0,file=rock-5b-plus_bookworm_kde_b2.output.img,format=raw \
       -snapshot \
       -serial mon:stdio \
       -display none

This path runs the image's DDR/TPL and SPL code, verifies all FIT loadables,
uses the FIT metadata to select the U-Boot load address dynamically, enters
U-Boot proper, and continues through its ``extlinux`` boot flow.  With the
Radxa Bookworm image, U-Boot loads the SDK kernel, initramfs, and
``rk3588-rock-5b-plus.dtb`` before printing ``Starting kernel ...``.

U-Boot to Linux Boot
--------------------

The complete U-Boot path uses a raw eMMC image that contains the Rockchip
firmware at LBA 64 and a boot partition with ``extlinux.conf``, ``Image``,
``initramfs.cpio.gz``, and a QEMU-generated RK3588 DTB.  The DTB embedded in
the image must be generated with the same ``-smp`` value used at runtime.

The locally verified downstream image boots with:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb \
       -smp 2 \
       -m 1G \
       -drive if=sd,index=0,file=build/agent/rk3588-uboot-linux/scratch/rk3588-uboot-linux-emmc-earlycon.img,format=raw \
       -nic user,model=gmac0 \
       -netdev user,id=vnet0 \
       -device virtio-net-pci,netdev=vnet0 \
       -serial mon:stdio \
       -display none

The verified ``extlinux.conf`` passes:

.. code-block:: text

   console=ttyS2,1500000n8 earlycon=uart8250,mmio32,0xfeb50000,1500000n8 keep_bootcon loglevel=8 rdinit=/init

U-Boot loads the kernel, initramfs, and DTB from eMMC, prints
``Starting kernel ...``, and the smoke initramfs reaches
``=== init done, exec sh ===``.

ZVM on RK3588 EVB
-----------------

The EVB ZVM smoke path uses an eMMC image and the upstream package's manual
copy sequence with ``mmc dev 0``.  Enable the optional ZVM RAM windows for this
machine, because the EVB board keeps them disabled by default:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588-evb,zvm-ram=on \
       -smp 8 \
       -m 1G \
       -drive if=sd,index=0,file=build/agent/zvm-rk3588/scratch/zvm-rk3588-qemu-emmc.img,format=raw \
       -serial mon:stdio \
       -display none

At the U-Boot prompt, run:

.. code-block:: text

   => echo loading ZVM img ...
   => mmc dev 0
   => fatload mmc 0:1 0x10000000 zvm_release_rk3588v2.bin
   => cp.b 0x103fd000 0x38800000 0x2f000
   => cp.b 0x1038b000 0x38600000 0x71958
   => cp.b 0x10319000 0x38400000 0x712e0
   => cp.b 0x102a7000 0x38200000 0x71178
   => cp.b 0x1023c000 0x38000000 0x6afc8
   => cp.b 0x1023b000 0x12afa000 0x4
   => cp.b 0x100f7000 0x129b6000 0x143570
   => go 0x10000000

The validated no-compatibility run reaches ``zvm_host:~#`` and starts the
bundled Zephyr guest.  This EVB image is useful for the ZVM host and basic
guest smoke path; use the ROC image below for the full Linux VM release-image
layout.

ZVM on ROC-RK3588S-PC
---------------------

The `RK3588 ZVM deployment guide
<https://esnl.hnu.edu.cn/zvm/document/deploy_rk3588.html>`_ targets the
Firefly ROC-RK3588S-PC board.  It expects an 8 GiB first FAT partition, a
second partition larger than 21 GiB, the boot files on the first partition,
and ``nrtos_images.bin`` written to the second partition with
``bs=1M seek=1024``.  The packaged file-system images are then written to the
second partition at 3 GiB-spaced offsets, leaving the first 3 GiB of that
partition for ZVM guest run records:

* ``android_vda.img`` at ``seek=3072``
* ``oh_vda.bin`` at ``seek=6144``
* ``linux_diskimg.bin`` at ``seek=9216``, ``12288``, ``15360``, and ``19432``

Download the ZVM release binaries from the official `ZVM RK3588 download page
<https://esnl.hnu.edu.cn/zvm/downloads/download_rk3588.html>`_.  The QEMU image
flow uses these release packages:

* ``kernel_images.zip``: provides ``kernel_images/`` with
  ``zvm_release_rk3588v2.bin``, ``boot.scr``, ``nrtos_images.bin``, and the
  raw images used by the package helper.
* ``file_system_images_part1.zip`` and ``file_system_images_part2.zip``:
  provide ``file_system_images/``.  Run its ``unpack.sh`` to produce the
  ``file_system_images/image/`` directory containing ``android_vda.img``,
  ``oh_vda.bin``, and ``linux_diskimg.bin``.

The Rockchip RKNS firmware binary, ``u-boot-rockchip.bin``, is separate from
the ZVM release package.  Use the RK3588 U-Boot build produced by the firmware
flow above, or another ROC-RK3588S-PC U-Boot build that emits the same combined
Rockchip image.

The release package also ships ``nrtos_imagespack.py`` with
``N = 0x1205000``.  For a raw QEMU TF-card image this means the second
partition must start at sector ``0x1005000`` so that ``seek=1024`` lands
``nrtos_images.bin`` at the absolute sector ZVM reads.  A more conventional
8 GiB-aligned second partition start of ``0x1008000`` puts the image 6 MiB too
late; ZVM then detects the slots but loads zero-filled Linux buffers.

The Linux kernel slot inside ``nrtos_images.bin`` must match the modules in
``linux_diskimg.bin``.  The release file system carries
``/lib/modules/5.10.110/kernel/zshm.ko`` with ``vermagic=5.10.110 SMP
mod_unload aarch64``.  If the first 64 MiB Linux kernel slot is replaced by an
unmatched kernel, Linux can still reach the Buildroot login prompt but
``zshm.ko`` fails to load and ZVM's operation-test heartbeat waits until the
Linux VM start timeout.  The local validated image uses the release
``Image.official`` 5.10.110 kernel in that slot.

To rebuild the boot payloads from the official package, run the package helper
from the ``kernel_images`` directory and choose option ``3``:

.. code-block:: bash

   $ cd build/agent/zvm-rk3588/work/kernel_images
   $ printf '3\n' | ./auto_py.sh

This regenerates ``nrtos_images.bin``, ``zvm_release_rk3588v2.bin``, and
``boot.scr``.  The helper runs ``raw_kernel_images/nrtos_imagespack.py`` first,
then ``raw_kernel_images/pack_img_v2.py``.  The first script packs the Linux,
Android, and OpenHarmony kernel/initramfs/DTB slots into fixed-size regions in
``nrtos_images.bin``.  The second script packs the ZVM segments listed in
``raw_kernel_images/segments.map`` together with the Zephyr and FreeRTOS helper
images into ``zvm_release_rk3588v2.bin`` and refreshes the U-Boot script.

The repository also provides a QEMU raw-image helper for the ROC board.  It
supports Linux hosts with ``dosfstools`` and ``mtools`` installed, and macOS
hosts through ``hdiutil`` and ``newfs_msdos``:

.. code-block:: bash

   $ ZVM=build/agent/zvm-rk3588
   $ KIMG=$ZVM/work/kernel_images
   $ FSIMG=$ZVM/work/file_system_images_official/image
   $ UBOOT=$ZVM/scratch/u-boot-roc-zvmcompat-build/u-boot-rockchip.bin
   $ OUT=$ZVM/scratch/zvm-rk3588-qemu-roc-sd-official-fixed.img
   $ scripts/zvm/rk3588s-roc-pc-make-zvm-image.sh \
       --kernel-dir "$KIMG" \
       --filesystem-dir "$FSIMG" \
       --uboot-rockchip "$UBOOT" \
       --output "$OUT" \
       --force

The script creates the 32 GiB raw card image, writes the MBR partition table,
formats both FAT partitions, copies ``zvm_release_rk3588v2.bin`` and
``boot.scr``/``boot.scr.uimg`` to the first partition, writes
``nrtos_images.bin`` to the second partition at ``bs=1M seek=1024``, writes the
Android/OpenHarmony/Linux file-system images at the offsets listed above, and
installs ``u-boot-rockchip.bin`` at LBA 64.

When diagnosing ``Timeout waiting for vm: linux_os-1 start`` or
``Failed to run linux VM 1, ret=-19``, check the image contents before changing
CPU or machine state:

* The ``nrtos_images.bin`` slot must be readable at the absolute sector
  expected by ZVM.  With the package's ``N = 0x1205000`` this means the second
  partition starts at sector ``0x1005000`` and the file is written to that
  partition with ``seek=1024``.
* The Linux kernel in the first 64 MiB of ``nrtos_images.bin`` must match the
  file-system modules.  A local test with a 7.1.0-rc7 kernel and the release
  5.10.110 root file system reached the Linux login prompt through
  ``zvm look 1``, but ``insmod /lib/modules/5.10.110/kernel/zshm.ko`` failed
  with ``invalid module format`` and ZVM timed out waiting for the heartbeat.
* The current model does not carry RK3588-specific EL2 FP/SIMD or PAN
  compatibility properties.  A validated no-compatibility run still reached
  ``Start VM Successful`` and ``[CREATE] linux VM 1 created and running`` for
  ``linux_os-1``.  If the release image times out, first check for a consistent
  ZVM Linux kernel and root file system.

Use the dedicated ROC machine and attach the prepared TF-card image as
``if=sd,index=2``.  The Rockchip RKNS firmware image in this card is read by
the QEMU BootROM from LBA 64 and U-Boot then exposes the same card as
``mmc 1``:

.. code-block:: bash

   $ build/qemu-system-aarch64 \
       -accel tcg \
       -machine rk3588s-roc-pc \
       -smp 8 \
       -m 1G \
       -drive if=sd,index=2,file=build/agent/zvm-rk3588/scratch/zvm-rk3588-qemu-roc-sd-official-fixed.img,format=raw \
       -nic user,model=gmac0 \
       -nic user,model=gmac1 \
       -serial mon:stdio \
       -display none

For repeatable local smoke tests, start from a fresh prepared TF-card image or
refresh the Rockchip RKNS firmware area at LBA 64 before each run.  The ZVM
package writes runtime state back to the card image; a reused scratch image can
otherwise fail in SPL with ``spl_load_simple_fit: can't load image loadables``
or ``mmc block read error`` before ZVM itself starts.

The validated firmware path reaches U-Boot proper after TPL/SPL checks the
ATF/U-Boot FIT loadables.  U-Boot bootflow finds ``boot.scr.uimg`` on the first
FAT partition and executes the package's load/copy sequence automatically.  If
autoboot is interrupted at the prompt, the same sequence can be run manually:

.. code-block:: text

   => echo loading ZVM img ...
   => mmc dev 1
   => fatload mmc 1:1 0x10000000 zvm_release_rk3588v2.bin
   => cp.b 0x103fd000 0x38800000 0x2f000
   => cp.b 0x1038b000 0x38600000 0x71958
   => cp.b 0x10319000 0x38400000 0x712e0
   => cp.b 0x102a7000 0x38200000 0x71178
   => cp.b 0x1023c000 0x38000000 0x6afc8
   => cp.b 0x1023b000 0x12afa000 0x4
   => cp.b 0x100f7000 0x129b6000 0x143570
   => go 0x10000000

The local smoke run loads ``zvm_release_rk3588v2.bin``, copies the packaged
guest images to their fixed addresses, initializes GMAC1, starts the bundled
Zephyr guest, detects the Android/OpenHarmony/Linux file-system slots, and
loads the Linux Image, DTB, and initramfs buffers from the corrected second
partition offsets.  The ROC board aliases GMAC1 as ``ethernet0``; GMAC0 is
also given a user netdev in the command above so the second modeled MAC is not
left without a peer.  The Linux guest console is configured by the package for
the PL011 at ``0xfeb50000`` using ``console=ttyAMA2,1500000`` and
``earlycon=pl011,0xfeb50000``.  ZVM keeps the host shell on the QEMU serial
terminal; after the Linux VM is running, connect the guest console from the ZVM
shell with:

.. code-block:: text

   zvm_host:~# zvm look 1

The validated run then shows the Linux Buildroot console on the same QEMU
serial terminal.  With a matching 5.10.110 kernel and ``zshm.ko``, ZVM reports
``Start VM Successful`` for ``linux_os-1``.

Known limitations
-----------------

The current model is intended for kernel and firmware bring-up smoke testing.
It does not model the closed PMU firmware or full EL3 MMU/xlat setup; the
RK3588 machine applies narrow runtime shims to enter BL31, keep BL31
initialization moving, hand off to U-Boot proper, and prepare the NonSecure
PSCI/GIC state U-Boot's Linux entry path expects.  U-Boot autoboot scans the
modeled eMMC/SDMMC, USB2, and GMAC boot devices and either boots the extlinux
test image or reaches the prompt when no boot image is present.  USB3 DWC3, a
real TRNG, and attached USB storage are not modeled.

Linux may print an ignored SCMI protocol-16 event registration warning, and the
PCIe legacy INTx irq-domain path is only stubbed; PCIe MSI/MSI-X is functional
through ITS.
