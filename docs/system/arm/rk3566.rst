Rockchip RK3566 Boards
======================

The ``microduck-beta`` machine models the MicroDuck beta board built
around the Rockchip RK3566 SoC.  It contains four Cortex-A55 CPUs, a
GICv3 interrupt controller and 1 GiB of RAM.

The machine boots a Linux kernel and device tree passed with ``-kernel``
and ``-dtb``.  The machine implementation does not model the BootROM, DDR
training, SPL, TF-A, OP-TEE or U-Boot boot stages.  The raw eMMC image is
attached as an SD card:

.. code-block:: bash

  $ qemu-system-aarch64 -M microduck-beta -m 1G \
        -kernel Image -dtb rk3566-microduck-beta.dtb \
        -drive if=sd,index=0,format=raw,file=microduck-beta.img \
        -serial mon:stdio

The first serial port is the Linux FIQ console and the second serial port
connects to the Dynamixel control bus.  The optional ``bluetooth`` chardev
serves the H4 Bluetooth transport on the third serial port.

The ToF input is provided by a dedicated ``tof-data`` chardev.  It
receives 192-byte depth frames for the VL53L8CX sensor: 64 little-endian
``uint16`` millimetre values followed by 64 target status bytes.

Camera pipeline
---------------

The camera path is modelled with the GC2093 sensor on I2C2
(``0xfe5b0000``, address ``0x37``), the RK3566 CSI DPHY at
``0xfe870000`` and the RK3566 ISP at ``0xfdff0000``.  The ISP IOMMU at
``0xfdff1a00`` translates the capture DMA addresses.  The GC2093 model
implements the 16-bit register interface, chip identification
(``0x2093``), soft reset, streaming control and register storage for the
sensor mode table, exposure, VTS, mirror/flip and gain registers.  The
streaming state is reported to the ISP through the model's streaming
GPIO.

The guest sees the ``rkisp_mainpath`` and ``rkisp_selfpath`` video nodes
as ``/dev/video0`` and ``/dev/video1`` plus the remaining rkisp capture
nodes.  When no ``camera`` chardev is attached the ISP generates a moving
colour-bar frame every 1/30 s, so the guest capture and 3A pipelines run
without a host frame source.  The optional ``camera`` chardev overrides
the generator with complete 640x360 UYVY frames that are converted to the
guest output format and written through the ISP IOMMU.  For example:

.. code-block:: bash

  $ qemu-system-aarch64 -M microduck-beta -m 1G \
        -kernel Image -dtb rk3566-microduck-beta.dtb \
        -drive if=sd,index=0,format=raw,file=microduck-beta.img \
        -chardev socket,id=camera,path=/run/camera.sock,server=on,wait=off \
        -serial mon:stdio

The ISP reports SOF and frame-end interrupts and writes the AE, AWB,
histogram and AF measurement blocks into the DDR statistics buffer, so
the vendor ``rkaiq_3A`` server can tune the running pipeline.

Known camera limitations: the ISP converts synthetic frames and does not
model the individual ISP processing blocks, so the captured image does
not originate from the sensor Bayer data; the 3A measurements are derived
from the synthetic frame.  The rkcif and MIPI CSI2 host models are not
implemented; the machine device tree fixup disables the corresponding
nodes.  The raw write/read and iqtool video nodes are visible in the
guest but do not produce data.

The camera, RGA2 and VENC models use libswscale, libavutil, libavcodec
and x264.  These devices are only built when the libraries are available
at configure time.

The models implement functional device behaviour and approximate timing.
The GPU, display subsystem, video decoder and the wireless SDIO data path
are not modeled.
